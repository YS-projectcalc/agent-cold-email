## Findings

### 1 · NON-BLOCKING for the dark merge · **BLOCKING BEFORE ARM** · lens 5/6 — reconcile reads the FIRST persisted spec while the direct resume path honors the LATEST call's input; when they diverge, an armed reconcile OVER-PROVISIONS on top

**Failure scenario (EXECUTED, reproduced):** on an armed `PROVISIONING_RECONCILE_ENABLED` tenant
with real spend armed:
1. `setup_infrastructure(persona="alpha", inboxesEach=5, domains=1)` lands DNS-pending → 202
   success-pending. Domain bought+committed; intent carries spec `alpha/5`; **0 mailboxes**.
2. DNS completes. A second **direct** `setup_infrastructure(persona="bravo", inboxesEach=2)` on
   the same ordinal takes the resume branch and provisions **bravo's 2 mailboxes** — the direct
   path passes `opts.personaSlug/opts.inboxesEach` (this call's input) straight to
   `provisionMailboxesForDomain` (`provisioning.ts:264-270`); the INSERT-only intent spec is
   never consulted on this path.
3. The reconcile sweep reads the intent's FIRST spec `alpha/5` (`provisioning-reconcile.ts:149,159`),
   sees `!dnsPending && liveMailboxes(2) >= inboxesEach(5)` is FALSE (`:150`), and re-drives with
   `alpha/5`. Mailbox addresses are `${persona}${ord+1}${idx+1}@domain`
   (`mailbox-provisioning.ts:132`), so alpha's 5 addresses are DISJOINT from bravo's 2 → all 5
   are freshly bought.

**Measured result:** final mailbox count **7** (`alpha11..15` + `bravo11,12`), `reconciled:1` —
for a customer whose LAST expressed intent was 2 mailboxes. Real vendor spend + monthly bill for 7.

**Lower-magnitude, MORE reachable sibling:** same-persona, reduced count. Call 1 `alpha/5`
pending; direct retry `alpha/2` provisions 2; reconcile reads `alpha/5` and tops up to 5 —
silently bumping a customer who *reduced* their ask back up to the first spec.

**Root class:** the persisted spec is authoritative for the reconcile path but NOT for the direct
resume path — two convergence authorities for the same ordinal. The design's claim ("the
INSERT-only spec makes a retry converge on the same deterministic addresses an agent retry would")
holds only when the agent's retry uses the SAME persona/count as the first call; a divergent
direct call + a later reconcile double-provisions.

**Blast-radius note:** the reconcile mailbox buys DO pass through `withSpendCeiling`
(`mailbox-provisioning.ts:340`), so `SPEND_CEILING_CENTS` bounds total spend — but
`assertWithinProvisioningCap` lives ONLY in `runSetupInfrastructure` (`provisioning.ts:418`), NOT
on the reconcile path, so the over-provision is capped only by the dollar ceiling, not the
intended mailbox count.

**Verification:** executed end-to-end through `runSetupInfrastructure` (×2) then
`runProvisioningReconcile` against a real TenantDO + sandbox mailbox adapter; asserted final
count/personas. A same-persona/same-count control converged to exactly 3 with a single domain buy
(refutes "reconcile always over-provisions").

**Why NON-BLOCKING for the merge:** (d) is 100% gated by `PROVISIONING_RECONCILE_ENABLED`
(unset default; `runProvisioningReconcileAllTenants` returns `{disabled:true}` before any DO is
constructed — verified). Nothing fires unarmed. **Why ARM-GATE:** the moment the flag is armed on
a tenant that has ever taken a divergent direct retry, the double-provision is live. Recommend one
of: (a) the direct resume path also reads the persisted intent spec (so the two paths cannot
disagree); (b) reconcile refuses to add a mailbox set when the domain already carries a
different-persona set; or (c) enforce persona/count as immutable-per-ordinal at the boundary.
Main loop owns the scope call.

## Attacks that FAILED (this is what makes the PASS meaningful)

**Lens 1 — the (b) reclassification boundary (the correctness crux). Every dangerous-direction
attack driven through the REAL `runSetupInfrastructure` catch; all held:**
- **Permanent DNS rejection, terminal ordinal** → `setDns` throws non-retryable → `notPropagated:false`
  → plain `VendorError`, THROWS (not 202). Executed: rejects `/permanently rejected/`.
- **Transient `/domains/list`-style API error, terminal ordinal** → `setDns` throws retryable →
  `notPropagated:false` (we never observed a not-ready answer) → ordinary retryable `VendorError`,
  THROWS, `provisioning` field absent. Executed.
- **Connected domain, not-propagated** → row `connection_type='connected'` → the pending
  reclassification requires `'purchased'` (`domain-dns.ts:257`) → plain retryable `VendorError`,
  THROWS. Executed.
- **Non-terminal ordinal pending** (domains=2, ordinal 0 pending, 1 unbought) →
  `inFlightOrdinal(0) !== input.domains-1(1)` → falls through to the retryable throw; only
  `...0.com` was ever bought. Executed.
- **Earlier ordinal permanently FAILS** (domains=2, ordinal 0 rejected) → loop throws at ordinal 0
  before the terminal ordinal is reached; ordinal 1 never bought → CANNOT be reported
  pending-success. Executed (the brief's explicit terminal-ordinal proof).
- **Controls (so the boundary isn't merely fail-closed everywhere):** a genuinely-benign terminal
  purchased pending DOES return `provisioning:"pending"`; a multi-domain terminal pending AFTER
  earlier ordinals fully complete returns `pending` with `pendingDomain` = the terminal name.
  Both executed. The terminal-ordinal invariant is sound because `provisionDomainWithMailboxes`
  THROWS (never silently returns) on any incomplete ordinal — DNS-pending re-drive throws before
  mailbox spend (`provisioning.ts:261-263`), so reaching the terminal ordinal means every earlier
  one fully provisioned.

**Lens 2 — the adapter change (not-yet-listed → all-false vs throw). Real `RealInboxKitDomainPort`
with a stubbed `fetch`; held:**
- 200 body `{error:true}` → `listDomainRecords` throws at `inboxkit-domain-port.ts:165` BEFORE the
  not-listed branch → `pollPurchasedDomainDns` THROWS `/domains\/list failed/`. Executed.
- HTTP 503 → `mapInboxKitError` throws → THROWS. Executed.
- **Control:** 200 body `{domains:[]}` (genuinely not listed) → returns all-false
  `DnsRecordSet`, no throw. Executed. The split (real API error throws; not-listed returns benign)
  is faithful — the benign `return dnsRecordSet(false)` (`:263`) is only reachable when
  `listDomainRecords()` RETURNED a list not containing the domain.

**Lens 3 — spend-neutrality of (d), no re-buy.** `recordDomainIntent` is `INSERT OR IGNORE`
(`provision-intents.ts:99`) → first spec wins. Reconcile re-drives via `provisionDomainWithMailboxes`,
whose resume branch is taken because `liveDomainForIntent` (filter `status != 'released'`) is
strictly BROADER than reconcile's own domain filter (`status='active' AND source='provisioned'`) —
so any domain reconcile matches, the resume branch also matches → **the buy path is never
reached** (proven: idempotent 2nd pass buys nothing; the convergence control did exactly one
domain buy). `domains.source` defaults to `'provisioned'` (`schema.ts:162`) so freshly-provisioned
domains match reconcile's filter (d is not inert). A released domain (`status='active'` fails) →
`continue`, never reaches a re-buy.

**Lens 4 — NULL-spec skip (Mordy-safety).** A committed intent with NULL `persona_slug`/`inboxes_each`
(the P0-rebound legacy shape) is skipped (`provisioning-reconcile.ts:136`), logged only when
DNS-pending, never re-driven, never spent. The P0 legacy-key rebind runs in the DO constructor
(`tenant-do.ts:215`) and leaves exactly this NULL-spec shape → skipped. Existing acceptance test
drives it (scanned:1, skippedNoSpec:1, setDns:[], mailboxCount:0).

**Lens 5 — replace: never touched.** Double-guarded: `intent.key.startsWith(replace:${tenant}:)`
→ `continue` (`:103`), AND `domainIntentOrdinal` returns `undefined` for any non-`tenant:#` key
(`:104-105`). Existing test: a fully-completable `replace:` intent under a ready port → scanned:0,
setDns:[], untouched.

**Lens 6 — flag OFF genuinely dark + not implicitly armed.** `provisioningReconcileArmed` reads
OFF for unset / `""` / `"0"` / `"false"` / `"off"` (case-insensitive). `runProvisioningReconcileAllTenants`
returns `{disabled:true}` and constructs NO tenant DO before the arming check. The
`spend-armed-env-coverage` categorization (`KNOWN_NON_SPEND_ARMING`) is CORRECT and does not arm
anything implicitly: the guard exists to force every VENDOR CREDENTIAL to be read by
`isRealSpendArmed` (which gates the simulate free-money bypass); `PROVISIONING_RECONCILE_ENABLED`
is a leg on/off switch, not a credential — the spend it drives is still gated by `INBOXKIT_*` /
`isRealSpendArmed` exactly as the on-demand path is. Tagging it `// spend-arming` would be WRONG
(it would demand `isRealSpendArmed` read a non-credential).

**Lens 7 — schema migration on an EXISTING DO.** `ensureColumnMigrations()` runs in the DO
constructor (`tenant-do.ts:198`) on every wake; `addColumnIfMissing` is `PRAGMA table_info` +
`ALTER TABLE ADD COLUMN` (`tenant-do.ts:` impl) — the N-3 CREATE-IF-NOT-EXISTS anti-pattern is
explicitly avoided (see its own comment). This is the identical primitive that migrated ~40 prior
columns onto live DOs. New columns are nullable → existing rows read NULL → reconcile skips them.

**Lens 8 — idempotency + fault isolation.** Second reconcile pass over a completed domain:
`!dnsPending && liveMailboxes>=inboxesEach` → `continue`, zero re-drive (existing test). One
tenant's failure is caught per-tenant in `runProvisioningReconcileAllTenants`; one domain's
failure is caught per-intent in `runProvisioningReconcile` (deferred/errors, next sweep retries);
existing per-domain-isolation test: good domain completes, bad domain deferred, neither aborts the
other. Leg ordering is below health/alerting, above the send pipeline (`scheduled.ts`).

## UNVERIFIABLE

- **True pre-migration DO (N-3 in the flesh).** The vitest harness builds every DO from the
  CURRENT `schema.ts`, which already contains `persona_slug`/`inboxes_each`, so I could not
  instantiate a DO whose `domain_intents` predates the columns and watch the ALTER fire. Mitigated
  to LOW risk by: the mechanism is the proven `addColumnIfMissing` ALTER (not CREATE-IF-NOT-EXISTS),
  it runs at every construction before any request, and it is the same primitive that has migrated
  ~40 columns on live DOs across prior waves. What would fully resolve it: a one-off manual apply
  against a copy of a real tenant DO, or a harness that seeds a DO from a frozen old schema.
- **Live InboxKit vendor semantics.** Whether InboxKit's real `/domains/list` returns
  `{error:true}` vs a non-2xx for the failure modes I stubbed is a vendor contract I can only
  read from the adapter's own comments, not exercise against the live API (dark). Both stubbed
  shapes throw, so the split holds for either; a live registration-latency race is unverifiable
  here.

## NEW (out-of-scope) observations — no verdict weight

- The reconcile path is bounded by `withSpendCeiling` but NOT by `assertWithinProvisioningCap`
  (which is only in `runSetupInfrastructure`). Independent of finding 1, an armed reconcile that
  re-drives many pending domains is dollar-capped but not mailbox-count-capped — worth a glance if
  (d) is ever armed at scale.
- `persona` is validated `min(1)` at the boundary, but `slugify(persona)` can still yield `""`
  (e.g. an all-punctuation persona). A `""` spec is NOT NULL, so reconcile would NOT skip it and
  would provision addresses like `11@domain`. Pre-C3 behavior (slugify predates this lane) and it
  converges (direct + reconcile both use `""`), so not a C3 defect — noted for hygiene.
