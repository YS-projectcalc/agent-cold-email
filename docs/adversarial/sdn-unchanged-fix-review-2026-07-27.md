One BLOCKING finding survives self-refutation: **the change does not stop the weekend alert storm it was

## Findings

### 1. BLOCKING — the fix does not resolve the reported weekend storm and adds false-RECOVERED flapping (lens 6 design, lens 1 spec-vs-code, lens 7 regression ring)

**Root cause.** The weekend "SDN list NOT loading" storm (streak #435) is generated by the Worker's own
direct refresh, not by the daily relay push. `maybeRefreshSdnList` runs on every 5-min ops-sweep tick; once
`fetched_at` is older than 24h it attempts a Treasury fetch (`sdn-refresh.ts:44-45`), which in prod always
525s (Worker egress is blocked — proven live, stated in `admin-sdn-ingest.ts:7-9`, `push-sdn.sh`, and the
07-24 review), throwing and calling `reconcileSdnAlert(success:false)` (`sdn-refresh.ts:51-52,:68`). That is a
~5-minute-cadence failure source. The new `"unchanged"` branch returns before `swapInSdnList`
(`sdn-ingest.ts:137-144`), so `fetched_at` is **not advanced** (`swapInSdnList` at `sdn-list.ts:152-161` is
the only writer of `fetched_at`). Therefore a weekend byte-identical push does nothing to quiet the direct
refresh — the 525 loop keeps firing every 5 min for the whole weekend.

This is exactly the invariant the 07-24 review depended on and that the diff now violates:
> "a successful ingest sets `fetched_at=now`, so `maybeRefreshSdnList` returns `"fresh"` and does NOT
> attempt/alert for ~24h … no cross-path thrash. Held." (07-24 review lines 99-100, 161-165)

The new code introduces a **successful ingest that does not set `fetched_at`**, so "the feared thrash
(always-failing direct refresh vs always-succeeding daily ingest toggling one streak)" — which that review
declared *prevented* — is now reachable.

**Concrete failure scenario.** Last real content swap Friday ~06:17 sets `fetched_at = Fri 06:17`.
- Sat 06:17: droplet relays the byte-identical weekend CSV → `"unchanged"`/200/success; `fetched_at` stays
  Fri 06:17. Streak is 0 at this moment → no email.
- Sat 06:20 onward: `fetched_at` is now >24h old → every 5-min tick 525-fails → `failure_streak` climbs
  (~288/day); emails at first-failure + every 6h.
- Sun 06:17: the next byte-identical relay push arrives with `failure_streak > 0` →
  `reconcileSdnAlert` sends a **false "[coldrig] SDN list load RECOVERED"** email and resets
  `failure_streak → 0`, `last_alert_ts → null` (`sdn-alert.ts:62-66`). The next 5-min direct-refresh failure
  hits the `failure_streak === 0` branch → **immediate, un-throttled "SDN list load failing" alert**
  (`sdn-alert.ts:73-77`) — a failure that under the old code would have been suppressed inside the 6h cooldown.
- Streak still climbs back to ~435 across the weekend as before; Monday's real content swap advances
  `fetched_at` and quiets it.

Net weekend volume ≈ old volume **+2 per daily unchanged-push-during-streak** (one false RECOVERED + one
un-throttled failure), and the founder now receives "RECOVERED" immediately followed by "failing" every day —
strictly worse than the honest "still failing" the old code produced.

**Arithmetic proof the diff targets the wrong path.** A `failure_streak` of 435 is 435 consecutive failed
attempts since the last success. The relay pushes once per day (`push-sdn.sh` cron `17 6 * * *`). 435
failures cannot accumulate from a once-daily source across a single weekend (the streak resets on every
weekday content swap). 435 requires ~5-min-cadence failures — i.e. the direct-refresh 525 loop — which the
diff does not touch. `push-sdn.sh`'s own comment says it plainly: "the Worker's OWN daily refresh attempt …
independently keeps retrying every ~5 minutes and ALREADY alerts OPS_ALERT_EMAIL on failure … a skipped relay
push just means that existing alert keeps firing until the next successful push." A successful *unchanged*
push is **not** a "successful push" in the sense that quiets the direct refresh, because it does not advance
`fetched_at`.

**Verification method:** traced sdn-ingest.ts:107-144 → sdn-refresh.ts:44-68 → sdn-alert.ts:54-89 by hand;
confirmed `swapInSdnList` is the sole `fetched_at` writer; corroborated the 525-every-tick premise against
three in-repo sources and the streak arithmetic; ran the alert/refresh co-run (the suite even contains
`ofac-sdn-refresh.test.ts > "20 consecutive failed 5-min ticks send exactly 1 email"`, confirming the 5-min
failure cadence model).

**Self-refutation attempted and failed:** (a) "maybe the direct refresh occasionally succeeds and advances
`fetched_at`" — refuted: three sources state Treasury 525s *every* Worker fetch; if it ever succeeded the
relay would be unnecessary. (b) "maybe `fetched_at` doesn't go >24h stale on weekends" — refuted: that is the
fix's own premise (no new publication → no swap → frozen `fetched_at`). (c) "maybe the 435 streak is only the
relay 422s" — refuted by arithmetic (once-daily cannot reach 435 in a weekend; the streak resets weekdays).

### 2. BLOCKING (same defect, alert-integrity face) — false "RECOVERED" desensitizes the operator

Under the old code a byte-identical weekend push was a failure and never emitted a recovery. Under the new
code every unchanged push landing during a (direct-refresh-driven) streak emits "SDN list load RECOVERED"
while the list is **not** recovering — the direct refresh is still 525-failing. A founder who trusts
"RECOVERED" and stops investigating can miss a genuine ongoing outage; the subsequent "failing" is easily
dismissed as a flap. This is the closest thing to the brief's feared alert-suppression vector. It is a NEW
regression introduced by this diff (folded into Finding 1's remedy; not independently shippable).

### 3. NON-BLOCKING / HELD — the stolen-token alert-suppression attack does NOT cleanly materialize

A stolen `SDN_INGEST_TOKEN` replaying the current byte-identical list gives **no clean "silence the failing
alarm" primitive**, precisely because `"unchanged"` does not advance `fetched_at`: the direct-refresh 525 loop
keeps firing failures, so an attacker's replays produce flapping (recovery + immediate re-alert = *more*
email), not silence. The genuine-staleness backstop is preserved: it lives in the direct-refresh path
(`fetched_at` > 24h → 525 → alarm), which `"unchanged"` does not extend; a feed that is genuinely stale for
weeks still alarms (in fact storms). So the replay/monotonicity posture is essentially **unchanged** vs the
07-24 baseline — held. (Ironically the same not-advance choice that defeats Finding 1's storm fix is what
prevents this suppression.)

**Residual to state honestly (pre-existing, out of scope):** the alarm that actually fires is "the Worker
cannot REACH Treasury" (525), not "the list content is N days old." `sdn-refresh.ts` swaps in whatever it
fetches with no content-age check, so a reachable-but-stale Treasury would raise no alarm. No content-age
alarm exists in the system — this diff neither adds nor removes one; do not read the fix as introducing one.

### 4. NON-BLOCKING — tests validate the relabel in isolation; the storm interaction is untested (lens 5)

The new tests never co-fire `maybeRefreshSdnList`, so they give false confidence that "the weekend storm is
fixed." No test reproduces the real scenario (direct refresh 525-failing every 5 min while the relay pushes
`"unchanged"` daily) — the exact case where the fix fails. Also `expect(after).toEqual(before)`
(ofac-sdn-ingest.test.ts) does **not** discriminate old-vs-new: the old code also performed no swap on the
second identical push, so `sdn_list_meta` was untouched there too. The load-bearing RED-on-old assertions are
`ok:true` / `reason:"unchanged"` / the mailer counts (those correctly fail on old code — CLAUDE.md rule e is
satisfied). No load-bearing old assertion was lost; the recovery-email test correctly pins exactly-one
recovery.

### 5. HELD — no caller misreads the no-swap `listVersion`

The `"unchanged"` outcome returns `listVersion = currentMeta.activeVersion` (the existing active version).
`admin-sdn-ingest.ts:47` passes the outcome through as JSON. `push-sdn.sh` checks only HTTP 200 and does not
parse `listVersion`; the ofac test asserts `listVersion === first.listVersion` (the existing version). No
caller, test, or tooling treats a 200 response's `listVersion` as "a new version is now active." Held.

### 6. Docs sweep — accurate as descriptions, but the effectiveness framing is false

`HANDOFF.md:31` and `tools/sdn-relay/README.md` accurately describe the ingest-path behavior (byte-identical →
`ok:true`/`"unchanged"`/200, no swap, `sdn_list_meta` untouched; a >10% entry-count drop still `"stale"`/422).
But the module doc comment (`sdn-ingest.ts:49-62`) and the test names frame this as the fix for the weekend
false-alarm incident — which it is not (Finding 1). Worse, `sdn-ingest.ts:57-60` states the no-op push leaves
"the Worker's own direct-fetch refresh … retrying on its normal cadence" as if that were a virtue — in prod
that cadence is the 525 storm. The comment describes the storm-preserving behavior as a feature.

## Recommended fix (pick one; keep the `"unchanged"` ≠ failure relabel — that part is correct)

- **(A) Preferred — advance `fetched_at` on a verified `"unchanged"` push.** The droplet *did* successfully
  fetch from Treasury and confirm the active content is current; that genuinely satisfies the
  "when did we last reach Treasury" freshness the direct-refresh guard keys on. Advancing `fetched_at` makes
  `maybeRefreshSdnList` return `"fresh"` for 24h → the 525 loop goes quiet → the storm actually stops. The
  alarm is preserved: if the relay *also* stops delivering, `fetched_at` goes stale → direct refresh 525 →
  alarm fires. (`push-sdn.sh` curls Treasury live each run, so byte-identical ⇒ Treasury is serving that
  content ⇒ genuinely current.)
- **(B) Alternative — the 07-24 review's own mitigation (its NEW finding, lines 128-132):** set
  `REFRESH_INTERVAL_MS` slightly longer than the daily relay cadence (e.g. 25h) and/or skip the direct-fetch
  attempt once the relay is the SDN source of truth, so the 525 loop stops firing between daily pushes.

Either way, add a test that co-fires the direct refresh (mocked 525) alongside daily `"unchanged"` relay
pushes and asserts the weekend email volume does not storm and no false "RECOVERED" is emitted.

### (a) Storm CLOSED — confirmed by trace + co-fire test

A daily byte-identical push now advances `fetched_at` → `maybeRefreshSdnList` returns `"fresh"`
(`sdn-refresh.ts:44-45`) → the 525 loop never attempts → no storm, no streak, no flapping. Walked the
arithmetic across weekend and 3+ day holiday patterns: as long as the relay pushes byte-identical at least once
per 24h, `fetched_at` stays <24h and every direct-refresh tick short-circuits to `"fresh"`. The only residual
email is the pre-existing 07-24 boundary-race noise (a *missed or slipped-past-24h* daily push → exactly 1
failure + 1 recovery, the intended backstop), never a storm. **Verification:** ran
`ofac-sdn-storm-interaction.test.ts` — passes; it seeds a real ingest, fires 3 direct-refresh ticks/day
(incl. the boundary-critical `+24h−5min` tick) across 2 days with daily unchanged pushes asserting ZERO
emails, then stops the relay and asserts the 525 alarm fires once `fetched_at` >24h.

### (b) Suppression re-opened by fix A — NON-BLOCKING (the alarm was never a stolen-token control)

My round-1 prediction was correct in mechanism: advancing `fetched_at` on `"unchanged"` DOES let a stolen
`SDN_INGEST_TOKEN` silence the direct-refresh staleness alarm by replaying the current byte-identical list
once per <24h (`fetched_at` stays fresh → the 525 alarm never fires → the frozen list sits alert-silent while
Treasury publishes unscreened additions). Round-1's byte-identical *reject* had blocked exactly this.

But it does **not** rise to blocking, and I graded it honestly by attacking my own alarm: **the freshness
alarm was never a control against a token-holder in the first place.** A stolen token could ALWAYS keep the
alarm silent — by pushing any within-10% *modified* list (current list ±a few entries, or with targeted names
removed), which is a real swap that advances `fetched_at` identically AND is strictly more powerful (actual
list tampering). So fix A grants no new suppression *capability* — only a marginally stealthier *variant*
(zero content change vs a ≥1-byte change), and even that leaves a monitorable anomaly (`fetched_at` advancing
while `active_version`/`content_hash`/`published_date` stay frozen for weeks). Round-1's byte-identical reject
had ~zero real security value (bypassable with a 1-byte edit), so removing it loses ~nothing. The honesty
statement's disclosed residual (`ofac-v1-honesty-statement-2026-07-23.md:138-146`: "token secrecy is the
PRIMARY control … a plausibly-sized list with specific names surgically removed passes both guards") already
subsumes replay-suppression as a strictly-weaker instance. The `"genuine-staleness backstop is PRESERVED, not
weakened"` claim in the module comment / HANDOFF / test name is true for the **non-adversarial** (droplet-down)
case — which is what the alarm is actually for — and the co-fire test proves that case.

### (c) `touchSdnListFreshness` narrowness — HELD

The SQL touches ONLY `fetched_at` (`sdn-list.ts:192`); it writes no `active_version`/`content_hash`/
`entry_count`/`published_date` and never touches `sdn_entries`. It is reached only AFTER parse succeeds, the
≥5000 floor passes, an active version exists, AND the candidate is byte-identical to the current active list
(`sdn-ingest.ts:144-167`) — so it cannot introduce a new version or rows and bypasses none of `swapInSdnList`'s
guards (it isn't a swap). A concurrent-swap TOCTOU on the shared row is benign (touch only sets `fetched_at`,
both writers use wall-clock `now`; a few-ms regression can't un-fresh a fresh list; ingests are serial from the
one droplet). Garbage/below-floor/malformed pushes do NOT reach it, so an attacker cannot advance `fetched_at`
with junk. Held.

### (d) Co-fire test cadence realism — HELD, with a minor coverage note

The test samples 3 ticks/day, not the full ~288, but that does NOT let a storm hide: the sample includes the
**maximal-staleness tick** (`+24h−5min`), and if the closest-to-the-boundary tick is `"fresh"`, every earlier
tick is fresher. The RED proof is well-targeted: the *first-cut* relabel (ok:true/`"unchanged"` but WITHOUT
`touchSdnListFreshness`) fails at the day-2 `+5min` tick (`fetched_at` still stale → refresh returns
`"failed"`, not `"fresh"`), isolating exactly the `fetched_at`-advancement contribution rather than the mere
relabel. Minor gap: the perfectly-aligned schedule (push always exactly at 24h) does not exercise the
late/slipped-push boundary race, so the "1 failure + 1 recovery on a late push" case is unproven — but that is
a known-accepted minor case, not a correctness defect.
