In `apps/platform/src/tenant-do.ts`, TenantDO methods are exposed over Cloudflare Durable Object RPC via `DurableObjectStub<TenantDO>`. Cloudflare's `Rpc.Provider<T>` mapped type computes `Serializable<R>` for every method's return type across the WHOLE class simultaneously. `engine/tenant-messages.ts`'s existing `TenantMessage.actionHint: Record<string, unknown> | null` (returned by `listMessages` → `MessageListPage`) already works fine as the FIRST such occurrence. Adding a SECOND RPC method whose return type also reaches a `Record<string, unknown>` field — even a byte-identical clone under a new type name, even via `type` alias instead of `interface`, even reusing the exact same `TenantMessage` type by intersection — makes `tsc` resolve the caller's `await stub.newMethod(...)` to `never`, with the ONLY diagnostic being `Property 'x' does not exist on type 'never'` at the CALL SITE (`routes/*.ts`), nothing pointing at the actual RPC return-type declaration as the cause.

Confirmed by bisection (isolated in `apps/platform/src/engine/tenant-messages.ts` while building `listMessagesForOperator`, the GET twin of the operator-message route, 2026-08-17): trimming the new type down field-by-field, the trigger was exactly `actionHint: Record<string, unknown> | null` — every other field (union string literals, `number | null`, plain `string`) was fine. Renaming the RPC method, converting `interface` to `type`, and reusing the identical `TenantMessage` type reference via `Omit<TenantMessage, "actionHint"> & {...}` all failed to fix it; only changing the FIELD's type from `Record<string, unknown> | null` to `object | null` fixed it (runtime-identical — same `JSON.parse(...)` value, `Record<string, unknown>` is a subtype of `object` so the assignment still typechecks fine).

**Why:** Cloudflare's `Rpc.Serializable<T>` recursive conditional type (`node_modules/@cloudflare/workers-types/index.d.ts` around line 14499) has a mapped-object branch keyed on an index signature; a SECOND independent object graph reaching a generic `Record<string, unknown>` (itself an index-signature type) appears to blow some internal TS instantiation-depth/complexity limit for that conditional, and TS silently falls to the `never` arm rather than emitting a `TS2589 excessively deep` diagnostic — so nothing in the compiler output names the real cause.

**How to apply:** any NEW TenantDO RPC method whose return type needs a "parsed arbitrary JSON object" field (actionHint-shaped, webhook payload-shaped, etc.) should type that field as `object | null` (or a specific named shape), never `Record<string, unknown> | null`, once ANY other RPC method on TenantDO already returns a `Record<string, unknown>`-bearing type. If a future `never`-at-the-call-site error shows up with no diagnostic elsewhere, bisect the new return type's fields exactly this way — don't assume it's about method/type naming, defaults, or `interface` vs `type` (all ruled out here). See `apps/platform/src/engine/tenant-messages.ts`'s `OperatorTenantMessage` for the working pattern + comment.
