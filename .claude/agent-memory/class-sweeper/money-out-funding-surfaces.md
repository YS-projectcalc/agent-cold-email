Added by the fundable-refusal / money-out-balance sweep (2026-08-18, ref `8c87c79`). See [[coverage-ledger]].

- **There are THREE grading surfaces per vendor, not one.** A brief saying "sweep every consumer of `mapInboxKitError`" UNDER-COUNTS by design: (1) `mapInboxKitError` handles only HTTP non-2xx; (2) InboxKit's app-level envelope is a **200 with `{error:true}`**, graded by nine hand-written per-method branches in `vendors/real/mailbox-port.ts` (:68,:121,:149,:212,:250,:269,:357) and `inboxkit-domain-port.ts` (:197,:243,:351) that never call the mapper and hard-code `false`; (3) `vendors/real/email-port.ts:149` is a DIFFERENT vendor (the cold-engine) with its own `RETRYABLE_ENGINE_STATUSES`. Grep `body.error`, `body.success`, `payment_type`, `typeof body.url` — not just the mapper's name.
- **The codebase may already NAME the class and still be in it.** `inboxkit-domain-port.ts:246-251` detects insufficient wallet balance explicitly (vendor returns a Stripe checkout URL instead of a wallet charge), comments it "permanent, operator-fixable (top up the InboxKit wallet)", and throws `retryable:false` anyway — same terminal customer wording as a bad-input rejection. A comment that names the operator remedy is EVIDENCE OF the class, not immunity from it.
- **`use_wallet_balance: true` is the money-out tripwire string.** Three call sites carry it or draw the same wallet: `mailbox-port.ts:64` (`/mailboxes/buy`), `inboxkit-domain-port.ts:228` (`/domains/register`), `mailbox-port.ts:145` (`/warmup/add`, credit-priced via `/warmup/pricing`). Grep it before trusting any money-out inventory.
- **A dispatch/attempt counter meant to cap DOUBLE-CHARGE risk is consumed by refusals that spent nothing.** `provision-intents.ts:301` `claimBuyDispatch` increments BEFORE the vendor call, `MAX_BUY_DISPATCHES = 2`; two zero-cost funds refusals permanently abandon the address (`abandonedPurchaseError`, `retryable:false`). Any pre-call claim counter is in-class for a fundable refusal.
- **The spend ceiling models OUR cost model, never the vendor's balance.** `engine/spend-ceiling.ts` reserves `SPEND_CEILING_CENTS` (our $/mo) + `INBOXKIT_PLAN_SLOTS` (subscription slots). Neither is the prepaid credit wallet, and the `'warmup'` arm returns **0** (:99) so the wallet-refused call reserved nothing. `docs/research/ga-gates-design-2026-07-22.md:134-138` explicitly deferred "does a buy past the slots draw wallet overage or hard-fail?" to arming — the design KNEW and the answer never landed.
- **`TenantOpsSummary` (engine/ops-summary.ts:18-48) carries OUR-side financials only** (usageCents, mrrCents, liability, dunning, decline codes). Zero vendor-side balance, so no digest/watchtower/admin surface can ever show a wallet. The 13 watchtower checks are all liveness/aging/pipeline; NONE is a vendor-funding check. `ACTIVATION.md` has no wallet-funding step either. Check the runbook AND the summary type, not only the check list.
- **Sandbox ports contain ZERO `throw` statements** (`sandbox/mailbox-port.ts`, `sandbox/domain-port.ts`). A funds refusal is unproducible in sandbox by construction — every funding-path test must drive the real adapter with a stubbed fetch (`stubFetchSequence`, `test/real-inboxkit-domain-port.test.ts`).
- **In-repo COMPLIANT template for the third grade:** `vendors/real/email-port.ts:64-77`'s `RETRYABLE_ENGINE_STATUSES = new Set([409, 422])` with a written per-status reason — 422 is graded retryable precisely because "the operator adds the mailbox to the engine creds file, after which a retry succeeds". The operator-actionable concept already exists on the engine seam and is absent on the InboxKit seam.
- **The customer vocabulary is published in FOUR places and all four must move together:** `error-response.ts:164` (the 502 body), `engine/retry-setup-message.ts:56` (`setup_failed` prose), `mcp/tools.ts:86` + `:350` (tool descriptions defining `terminal`), `site/openapi.yaml:2184-2188` (the `severity` enum) + `:1509-1527` (the `VendorError` response schema).
