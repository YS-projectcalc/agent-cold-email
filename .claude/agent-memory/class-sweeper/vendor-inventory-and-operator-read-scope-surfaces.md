Added by the C/D sweep (2026-08-18, ref `8c87c79`), after the mordytee12 paid-and-unadopted incident. Extends [[coverage-ledger]] and [[monitoring-completeness-surfaces]].

- **The port TYPE is the ceiling on any reconcile.** `DomainPort.listOwnedDomains()` exists (`packages/shared/src/vendor-ports.ts:170`); `MailboxPort` has NO list method at all — only `provisioningState(email)`, which requires already knowing the address. So the mailbox half of a vendor-vs-platform diff is UNBUILDABLE without a port change, even though `/mailboxes/list` supports a paged walk. Check the PORT surface before scoping any reconcile guard.
- **The vendor-side enumeration that does exist lives OUTSIDE the repo.** The 2-hourly operator watch cron (`HANDOFF.md:24`, state at `~/.claude/mordy-watch/last-seen.json`) pulls `POST /domains/list` + `POST /mailboxes/list` and had mordytee12 in its own state file — but it diffs against hand-maintained BASELINES, not platform rows, and is session-scoped. Never credit it as a platform detector.
- **The `mailbox_intents` / `mailbox_buy_dispatches` blind spot is the cheapest member and needs NO vendor call.** Both are read ONLY by their own writer module (`engine/provision-intents.ts`) and ONLY by key. Zero status scans, zero watchtower checks, zero admin reads. A `bought`/`dangling`/`warming` intent = money spent with no `mailboxes` row and no detector. Contrast `domain_intents`, which HAS both a scan (`provisioning-reconcile.ts:92`, DARK) and an admin read (`provisioning-state.ts:106`) — the domain/mailbox asymmetry is the finding.
- **Every watchtower signal derives from `getOpsSummary` (`engine/ops-summary.ts`), which reads only `mailboxes` / `domains` / `mailbox_cred_pushes` / `scheduled_sends` / `events`.** All 13 check names (`d1`, `do_storage`, `engine`, `failure_signals`, `cron_sweep`, `cron_legs`, `warmup_cancel_gave_up` + 6 per-entity prefixes in `watchtower-alerts.ts:98-118`) are platform-row-derived. Confirm this before asserting any vendor-side detector exists.
- **`vendor_spend_entries` has NO resource-identity column** (`migrations/0011_vendor_spend_ledger.sql:47-57`: id, period_key, tenant_id, kind, cents, status, timestamps). A committed 'mailbox' spend cannot be joined to a `mailboxes` row, so even the pure-D1 reconcile ("committed mailbox spends vs live rows") is not expressible in the current schema. The schema-can't-express rung again.
- **`vendor_slot_state.slots_used` drifts UP permanently** on a buy that commits and then fails before `insertProvisionedMailbox` — `releaseMailboxSlots` decrements off `mailboxes.slot_counted` rows only (`lifecycle.ts:273,309`). No admin read exposes it. Money-relevant and silently shrinking the platform's own capacity gate.
- **`warmup-cancel.ts:73` selects `FROM mailboxes`** — a warmup subscription enrolled for an address with no row is never cancelled and never considered. The one existing reverse-direction check, `warmup_cancel_gave_up` (`sweep-signals.ts:134`), is a 24h WINDOWED count and self-clears on a timer.
- **A prior gate saw the exact Class-D defect from the WRONG SIDE.** `docs/adversarial/admin-read-endpoints-gate-2026-08-17.md` F3 flagged `LIKE 'setup_infrastructure:%'` as over-matching (`_` is a wildcard) and graded it non-blocking/latent. The incident's defect is the opposite direction — under-inclusion of `provision:mbx:*`. When a gate has already touched a line, read WHICH direction it reasoned about.
- **`count` fields computed as `list.length` after a LIMIT.** `/admin/ops/waitlist` (`routes/admin-ops.ts:81`) returns `count: entries.length` over `listWaitlistEmails(env, limit=1000)` while an unfiltered `countWaitlistEmails` exists and is used only by the digest. `/admin/screening/reviews:22` does the same over a `status='pending'` filter. Grep `count: <x>.length` on every list route.
- **In-repo COMPLIANT template for the whole D class:** `listMessagesForOperator` (`engine/tenant-messages.ts:394-436`) — clamped `limit`, `unreadOnly` defaulting to ALL, and a `total` computed over THE SAME `where`, with the rationale written in the doc comment. Its own gate sibling (`provisioning-state.ts`) shipped without any of it; cite the pair.
- **No `/admin` path appears in `site/openapi.yaml`** (35 paths, zero admin) — the admin surface has no machine-readable contract, so a field-name-vs-scope lint has nothing to check against and must be source-side.
