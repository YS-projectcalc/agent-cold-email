Added by the monitoring-completeness sweep (2026-08-17, ref `9d3ec7e9`). Cover these before declaring a completeness/observability inventory done. Extends [[coverage-ledger]].

- **The strongest members have NO `WHERE` and NO `LIMIT`.** Grepping filters + bounds under-counts by ~30% on this class. Three spellings, not one: (a) enum allowlist, (b) bound/page, **(c) substrate-or-config split** — a hardcoded constant (`admin/ops-sweep.ts:624` `provisioningFailureCount: 0`, mirrored into the watch's state file and read as evidence), a skip-dark check (`admin/watchtower.ts:110-123` omits `engine` entirely when `ENGINE_BASE_URL` is unset — an env var loss DELETES a check with no row and no symptom), or a two-store split (`d1`/`cron_sweep` in WatchtowerDO, never in `watchtower_state`). The invariant they all break: **absence is indistinguishable from health**.
- **Check the COUNT half AND the LIST half — they are usually blind together.** `countSupportTicketsByStatus` (`admin/db.ts:163-171`) hardcodes the SAME two statuses as `SUM(CASE)` columns that `listOpenAndEscalatedSupportTickets` filters on, so a count-vs-list cross-check AGREES while both miss. Never credit a digest's own counts as a completeness check; find the unfiltered `COUNT(*)`.
- **"Complete by accident" — grep for writers of every enum value.** The support digest is complete only because `'closed'` has **zero writers** in src despite existing in the TS union (`admin/db.ts:20,134`). A type union member with no writer is a class member waiting for its first feature.
- **No status column in this repo has a CHECK constraint** (all 17 migrations scanned). The enum is anchored only in TS. But the repo DID apply the reasoning deliberately once — `schema.ts:220-221` chose a separate column over a third `dns_status` value because "every reader branches on `dns_status != 'ready'`". Cite that precedent when proposing the CHECK guard.
- **Watch spec vs its state file DRIFT is its own finding.** `HANDOFF.md:20` enumerates 4 legs; `~/.claude/mordy-watch/last-seen.json` carries an `opsDigest` block only `/admin/ops/digest` can produce — an undocumented 5th leg a resuming session silently drops. Always diff the documented leg roster against the fields the state file actually persists.
- **A "staleness tell" depends on WHICH rows get rewritten each cycle.** Leg 3's dead-cron tell (stale `updatedAt` >15min) works only because `do_storage` is pushed unconditionally (`admin/watchtower.ts:106`); `failure_signals` (dead band), per-entity checks (only while unhealthy), `cron_legs` (only on a graded streak) and `engine` (only when configured) all freeze with a perfectly live cron. Trace which checks are reported EVERY sweep before trusting any freshness heuristic.
- **In-repo COMPLIANT templates to cite instead of inventing one:** paginated vendor reads = `vendors/real/inboxkit-domain-port.ts:162-181` (walks `body.pages`, THROWS at the ceiling) and `vendors/real/mailbox-port.ts:241-261` (returns `"inconclusive"`); bounded sweep = `runSendPipelineAllTenants` (`admin/ops-sweep.ts:471-503`: reports `skippedForLegDeadline`/`budgetExpiries` into `sweep-signals.ts` → `cron_legs`, plus cycle-derived rotation for eventual coverage); truncation-on-the-wire = `engine/activity.ts:40-80` (`limit+1` → `hasMore` → `nextCursor`).
- **The read's column list is part of the class.** `admin/db.ts:157` drops `email_sent_at`, so no surface distinguishes "the founder was emailed this ticket" from "nobody was" — even though the column exists and is written. Score SELECT column lists, not just WHERE clauses.
- **The watch cron prompt is NOT on disk** (session-scoped; `~/.claude/mordy-watch/` holds only `last-seen.json`, no crontab, no `~/.claude/crons`). Watch-side findings are inferable only from `HANDOFF.md:20` + the state-file shape — say so rather than asserting the leg's logic.
