Search-coverage ledger for `~/dev/coldstart`. One line per surface that a sweep can easily miss. Cover these BEFORE declaring an inventory complete.

- **Downstream consumers of a raw signal**, not just its handler. The bounce-suppression bug (`reply-processor.ts`) also feeds `deliverability.ts::gatherMailboxHealth` bounce COUNTS → `evaluate` PAUSE/REPLACE_DOMAIN thresholds → real vendor spend. A sweep that stops at the write site misses the reputation/action loop that re-reads it.
- **Vendor-port ERROR CONTRACT (`packages/shared/src/errors.ts`)** is the systemic root of the retryable-vs-fatal class: `NotActivatedError`/`ValidationError` carry no severity/`retryable` flag, so every `real/` adapter throws an unclassifiable error. Check the contract, not only the call sites.
- **Sandbox adapters mask the missing branch** — always diff sandbox fixture shape vs real contract. `sandbox/email-port.ts` only emits hard bounces; `PolledBounce` has no severity field; `test/helpers.ts` `invoice.payment_failed` carries no decline-code. The other branch is untested BY CONSTRUCTION.
- **Stripe webhook `obj` payload fields dropped on the floor** — `billing.ts` reads `obj.status`/`obj.id` but never the decline reason/code on `invoice.payment_failed`. Grep for the event type AND check which sub-fields the handler ignores.
- **Schema can't EXPRESS the distinction** — `suppressions` PK `(tenant_id,email)`, `reason TEXT`, no `severity`/`expires_at`; `PolledBounce`/`events` have no severity column. A guard that only lints code misses that the storage layer forbids a soft/temporary suppression.
- **Cron/RPC lanes duplicate engine entry points** — `scheduled.ts` → `admin/ops-sweep.ts` re-invokes deliverability + dunning per-tenant; a class present in the engine fn is present in the cron lane too. (Prior general lesson: migration SQL, drift scripts, docs, CI config under-counted elsewhere — none present in this repo, but check `wrangler.toml` crons + any `spikes/` real-server code, which is out-of-scope here but is where the real contract lives.)
- **TIME-BASE PROVENANCE — the surface that beat the 2026-08-05 spend sweep.** ⚠️ **CORRECTED 2026-08-17 at ref `9d3ec7e9` — the old form of this entry was STALE and nearly produced a wrong finding.** The frozen-paid-clock defect is CLOSED: `engine/clock-migration.ts` shipped (founder ruling 2026-08-05, wave-2 DECISION 2), `clock.ts:6-14` states RealClock is every non-sandbox tenant's clock, and `tenant-do.ts:268` (`clock_mode === 'real'` → RealClock), `:274-276` (one-shot migration at boot), `:294-301` (`switchToRealClock`), `:584` (`paid ? new RealClock() : …`) implement it. What REMAINS live: demo/free tenants run a VirtualClock at up to 1440×, so every window measured on `ctx.clock` (`tenant-messages.ts:73,195,249`, `threads.ts:136`, `idempotency.ts:71`) is up to 1440× NARROWER in real time than its constant claims — a 30-day TTL expires in ~30 real minutes. `contact-operator-guard.ts:30-32` deliberately uses RealClock to dodge this; most other windows do not. Still grep `clock\.now()` vs `new RealClock()` vs raw `Date.now()` — but VERIFY the migration's writers before asserting either direction. **General lesson: a ledger entry naming a defect is a claim about a past ref; re-verify it against HEAD before building a finding on it.**
- **Sandbox masks time-base bugs BY CONSTRUCTION** (second incarnation of the sandbox-masking lesson): `SandboxMailboxPort.startWarmup` returns `this.clock.now()` (virtual, consistent) while `RealMailboxPort.startWarmup` returns `Date.parse(vendor.started_at)` (real). Every ramp/cancel test is green in sandbox and wrong on the real path. Always diff the sandbox adapter's timestamp SOURCE against the real adapter's.
- **A coverage test that `?raw`-imports ONE file is a coverage LIE.** `spend-ceiling-coverage.test.ts` parses only `engine/provisioning.ts` and pins `allSites.length === 3`; any money-out call added in another file is invisible AND the pin still passes. Check what the guard's SOURCES array actually contains before crediting it.
- **Ground ref matters**: sibling chats mutate this repo. Sweep of 2026-07-12 pinned `d4937ce1a9565261cc6f394451b8a2ced499cce2`; engine code was clean, only `site/` + docs dirty. Added by the partial-state-saga sweep (2026-08-05, ref `5c9f5877`):
- **The discriminator is an `await` on real I/O BETWEEN durable writes — not "multi-step".** A DO commits all writes in one event-loop turn atomically, so a fully-synchronous handler (`launchCampaign`, webhooks CRUD, `dashboard-views`, `suppression`, `thread-labels`, `mailbox-state`, `ops-summary`) is immune BY CONSTRUCTION. Grepping "files with many writes" over-counts; grepping `await` under-counts (default-param evaluation + awaits inside called helpers). Score each file `writes>0 AND awaits>0`, then read the ORDER.
- **Check the idempotency WRAPPER, not just the handler.** `withRequestIdempotency` DELETEs its claim row in `catch` — so a partial failure erases the only evidence the run started and the retry re-executes from step zero. It is the class amplifier; any member wrapped in it inherits the re-run behavior.
- **Cross-store (DO SQLite + D1) sequences have ZERO atomicity and no anchor row** — a surface with no SQL in the file at all. Members: `routes/signup.ts` (D1 index → `initTenant`), `admin/terminate.ts` (DO teardown → D1 status → D1 audit), `routes/admin-screening.ts` reject, `routes/login.ts` `/login/consume`. Sweep the ROUTES and admin orchestrators, not only `engine/`.
- **A claim-before-execute row that is NOT released on failure is the mirror-image defect**: `applyStripeWebhookEvent`'s `webhook_events` INSERT OR IGNORE persists through a later throw, so Stripe's redelivery is swallowed as a duplicate and the remaining steps never run. Grep for `INSERT OR IGNORE`-as-claim and ask what happens to it on throw.
- **Docs/tool-descriptions/openapi CLAIM the missing mechanism** — `ARCHITECTURE.md:18` and `SPEC.md:69` describe a "ProvisioningDO resumable saga"; `mcp/tools.ts:67` + `site/openapi.yaml:81/94` promise `{jobId}` + "poll for progress". No job record exists (`newId("job")` is fabricated at return). The claim surface IS part of the class inventory.
- **In-repo COMPLIANT templates to cite instead of inventing a pattern**: `withSpendCeiling` (reserve→execute→commit/release + `reapStaleReservations`), `runTick`'s pending→sending claim + `SEND_CLAIM_TTL_MS` reclaim, `swapInSdnList` (shadow-write→atomic pointer flip), `sendWithGuards` (reserve cap→send→release), `mailbox_cred_pushes` (record 'pending'→push→mark 'pushed' + reconcile sweep).

Added by the signal-inversion sweep (2026-08-17, ref `9d3ec7e9`) — see [[signal-inversion-surfaces]]:
- **A CLAIM about a side-effect is a member even when no "message" is emitted.** The biggest sub-family was the phrase *"The operator has been notified"* (7 sites: `error-response.ts:88,126`, `mailbox-acquisition.ts:260,273`, `spend-ceiling.ts:199-200`, `openapi.yaml:1508`) — composed by the code that REQUESTED the alert, never by the code that sent it. `NotActivatedError` has NO notifier anywhere. Always grep the customer-facing prose for asserted side-effects, then trace whether the notifier can early-return (no `OPS_ALERT_EMAIL`), swallow (`trySend`→false), or be SUPPRESSED by a cooldown/debounce.
- **The VOCABULARY is a sweep surface.** `severity` published as `enum [info, action_required]` (`site/openapi.yaml:2157`) with a bare `string` TS type and no DB constraint means a correctly-emitted terminal message is indistinguishable from a retryable one. An emission fix that doesn't add the rung re-opens the class one layer up. Check the enum/type/CHECK-constraint trio for every signal field.
- **Clear-claims cluster within ~40 lines of each other.** F10 (`watchtower.ts:285`) had TWO uncaught siblings at `:307` and `:322` in the same function, each inferring a positive cause from absence-from-a-filtered-query. When one clear site is a member, read every other `healthy: true` producer in the file before moving on (`grep 'healthy: true'` found all 9 tree-wide).
- **Windowed counts self-clear on a timer.** `sweep-signals.ts:126` reports healthy on `gaveUp === 0` where `gaveUp` is a 24h digest window — a RECOVERED email for vendor subscriptions still billing. Any check whose healthy predicate is `count === 0` over a trailing window is an arm-B candidate by construction.
- **`policyFor`-style ALLOWLISTS are the arm-A tripwire.** `watchtower-alerts.ts:134-157` exempts only 2 prefixes from the 2-observation debounce; the DEFAULT is debounce, so the next event-driven `reportCheck` caller is silenced forever. No live member today (all per-entity checks are re-observed each sweep) — but check the exemption list against the set of one-shot producers on every future alerting sweep.
- **In-repo COMPLIANT templates for this class**: `alertMailboxResolved` (clears only after `awaitMailboxReady` PROVES the state, and only for a previously-flagged entity), `mailbox-provisioning.ts:275-324` (each terminal branch gets its OWN check name so a cooldown can't dedup it away), `ops-sweep.ts:89-92` (emails only after `suspendForDunning()` returns true), `contact-operator-guard.ts:143` (`needs_human` BYPASSES the throttle — severity gate in the right direction).

Added by the head-of-line-blocking sweep (2026-08-17, ref `9d3ec7e9`):
- **A STALL is a starvation mechanism with no `catch` to grep for.** `reply-processor.ts:262` HAS per-mailbox try/catch and is still fully in-class: all mailboxes share ONE `SEND_PIPELINE_TENANT_BUDGET_MS` (135s) while a single poll may burn `ENGINE_REQUEST_TIMEOUT_MS` (120s), and the mailbox query has NO `ORDER BY`. Read the 5-rung ordering ladder at `vendors/real/email-port.ts:35-61` before judging any budget-bearing loop. Grep set for the stall variant: `BUDGET_MS`, `DEADLINE_MS`, `TIMEOUT_MS`, `Promise.race`, plus "does the item query have an ORDER BY / rotation offset?"
- **Permanence comes from deterministic RE-SELECTION, not from the loop.** A loop only starves within one call; what makes it permanent is the next call re-deriving the same ordered list (`domainIntentKey(tenantId, ordinal)`, the deterministic `persona{n}{m}@domain` addresses, the fixed lookalike prefix list). Score each loop on all three: sequential + head-can-consume-the-call + stable re-selection.
- **An `await` placed just ABOVE a function's own `try` reads as isolated and is not.** `deliverability-actions.ts:166` `await releaseMailboxes(...)` sits above the `try {` at :168 whose `catch` everyone cites as the isolation proof. Also check the catch's own re-throw arms (`:241` re-throws non-`VendorError`).
- **A guarded inner loop nested in an UNGUARDED outer loop is still a member** — `applyReplaceDomain`'s internal catch is irrelevant to `applyActions:406`, which has none, and that escapes to the unwrapped `tick.ts:165` (the warmup sweep below it IS wrapped — the asymmetry is easy to misread).
- **The anchor row's PLACEMENT decides whether a mid-loop throw is retryable or a permanent restart-and-re-die.** `teardownTenant` writes `teardown_records` only after its domain loop, so the early-return idempotency guard never arms and the whole teardown re-runs into the same failing domain forever.
- **`apps/engine/src` is a second service with its own loops** and the platform's per-item catch does NOT rescue it: `engine.ts:237` + `classify.ts:99` (`await simpleParser` unguarded) starves a mailbox permanently because the platform deliberately leaves the consumer-owned `poll_cursor` un-advanced. Sweep `apps/engine`, `packages/cli`, `packages/shared` — a `apps/platform/src`-only glob under-counts, and so would a tripwire test globbing only `../src/**`.
- **Compliant templates for THIS class, all in-repo:** `ops-sweep.ts:463-503` (rotation offset + `withTenantBudget` + leg deadline — the model for pushing fairness one layer down), `warmup-cancel.ts:87` (catch + attempt counter + `*_gave_up_at` marker), `provisioning-reconcile.ts:97` (per-item catch → `deferred`/`errors`) — but that last one **SHIPS DARK** (`PROVISIONING_RECONCILE_ENABLED`, audit F5), so never cite it as an active mitigation.
- **`test/send-governance-coverage.test.ts` is the house tripwire idiom** (`import.meta.glob(..., {query:"?raw"})` + an `ALLOWED_*` map with a written reason per entry, + self-tests against synthetic sources so the detector can't rot). Propose new structural guards in that shape, and state its glob roots explicitly.

- **`.sql` migrations vs `tenant-do.ts` runtime DDL are TWO surfaces.** Schema lives both in `apps/platform/src/schema.ts` (canonical CREATE) and `tenant-do.ts`'s `addColumnIfMissing`/`ensure*Index` runtime backfills. A column/index can be added in one and not the other. Sweep both.
