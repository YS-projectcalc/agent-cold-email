From the 2026-08-17 sweep (ref `9d3ec7e9`, 14 IN / 21 OUT / 3 UNCERTAIN). The class is NOT "records the word pending" — it is **terminality inferred from a PROXY** (fn returned without throwing / a row exists / a marker was written / a dedup key matched) instead of asserted by the outcome. Three spellings: (a) return-implies-done, (b) marker-before-confirmation, (c) absence-implies-success.

- **Enumerate EVERY `return` of a wrapped fn — grepping non-terminal KEYWORDS under-counts badly.** Two of the three members inside `runSetupInfrastructure` carry no `"pending"` token at all: `provisioning.ts:429` (`quoteOnly` preview) and `:626` (`CapacityPendingError` graceful catch, which returns the FULL-SUCCESS shape `{jobId, billing}` with no discriminator). Only `:657` looks non-terminal to a grep. Read the function; don't pattern-match its payload.
- **A tool description that instructs a MULTI-CALL FLOW is a reachability spec no grep finds.** `mcp/tools.ts:74` tells the agent "pass quoteOnly:true first … before committing"; `quoteOnly` and `idempotencyKey` ride the same tool input (`mcp/schemas.ts:51`) and the same HTTP header (`routes/infrastructure.ts:14`). That documented happy path is more reachable than any crash/DNS-stall member. Read tool descriptions + openapi as call SEQUENCES, not prose.
- **`grep "NOT NULL DEFAULT '"` over `schema.ts` + all `migrations/*.sql` is a first-class pattern for this class.** Found `request_idempotency.status DEFAULT 'done'` (the replay table defaults to TERMINAL) and `domains.dns_status DEFAULT 'ready'` (BYO inserts at `byo-intake.ts:191` omit the column, so unverified rows land 'ready'). Ask of every enum column: is the DEFAULT the safe/incomplete value or the finished one?
- **A helper returning a boolean nobody reads = the marker lies.** `watchtower-alerts.ts:222` `trySend` returns false on a dark/failed send; all three callers (`watchtower.ts:358`, `watchtower-infra.ts:55`, `watchtower-do.ts:147`) advance `last_alert_ts`/`alert_count` regardless. `migrations/0008` documents the column as "actually SENT". Grep for send/push helpers whose return value is discarded.
- **"Clear the alert because it left the unhealthy set" repeats — sweep ALL clear branches, not the one the audit named.** `watchtower.ts:284` (F10, the known one), `:307` (cred-push, and it fires precisely because the revoke tombstone left the 'pending' set), `:322` (send-starved). Each announces a POSITIVE fact it never re-read.
- **Ask of every swallowed-error write: what SELECT ever picks this row up again?** `lifecycle.ts:208-213` tombstones `mailbox_cred_pushes` `'revoked'` BEFORE a revoke that swallows failures; the only reconcile lane selects `status='pending'` (`mailbox-credential-push.ts:252`). The tombstone-first ORDERING is deliberate (CREDSTORE F2) — the fix is a distinct unconfirmed state, never moving the write.
- **In-repo templates to cite instead of inventing a pattern**: `apps/engine/src/store.ts` dangling→park→424 (an unverified dispatch is NEVER recorded as sent — the gold standard); `warmup-cancel.ts:126` give-up in its OWN column + ops action row ("both columns stop the sweep; only one is evidence the charge stopped"); `agent_contact_log.emailed_at` released on send failure (`contact-operator-guard.ts:227`); `launchCampaign` THROWING `DuplicateCampaignError{existingCampaignId}` vs `contactOperator:63` returning a byte-identical success on dedup.
- **The blocking test can be a coverage LIE by fixture, not by SOURCES array.** `test/idempotency.test.ts:72` exercises `setup_infrastructure` replay under SANDBOX adapters where the provision always completes — it proves only the terminal case and is blind by construction to all three non-terminal returns. Second incarnation of the sandbox-masking lesson; see [[coverage-ledger]].
