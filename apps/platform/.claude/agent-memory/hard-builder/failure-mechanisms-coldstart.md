Running list of failure mechanisms proven by code-trace/live evidence in `apps/platform`. One line each; verify against current code before acting on any of them.

- **Paid tenants run a FROZEN clock.** `VirtualClock.now() = base + offset` (src/clock.ts) has no wall-clock term, and both offset writers (`TenantDO.advanceClock`, `engine/demo.ts`) are demo/free-only. Signup always creates plan `demo` (routes/signup.ts), checkout only flips `plan` (engine/billing.ts) — so every timestamp a paying tenant writes via `ctx.clock.now()` is stuck at its pre-upgrade instant. Consequence: D1/DO rows look "missing" when queried by date, `periodKey` never rolls over, `epochDay` counters never reset, and cron reapers (which use `RealClock`) see every fresh row as instantly stale.
- **DO SQLite writes survive a thrown RPC** (proven live 2026-08-04: the `tenant_profile` brand UPDATE persisted through a 500). So "row absent" ⇒ that line never executed — a valid bisect signal.
- **`app.onError` maps by `err.name` only** (src/index.ts). `VendorError`/`NotActivatedError` are unmapped ⇒ opaque 500. The MCP surface (src/mcp/handler.ts tools/call) instead returns HTTP 200 + `isError:true` + `err.message`. Same error, two very different-looking symptoms depending on surface — never infer the error class from the customer-visible shape.
- **The `real` adapter bundle hands out throwing stubs.** `RealBillingPort`, `RealDnsScanPort`, `RealDomainReputationPort`, `RealMetricsPort` all throw `NotActivatedError`. Any code path that touches them for an activated tenant dies mid-saga, after real vendor spend.
- **Changing a durable key's DERIVATION orphans every row written under the old shape, and an orphaned purchase-intent re-enters the "never bought" branch — i.e. it re-spends.** Proven live 2026-08-12: `domainIntentKey` went from the inline `${setupKey ?? `tenant:${tenantId}`}#${ordinal}` to `tenant:${tenantId}#${ordinal}` (85f48af) with no backfill, so tenant ten_91aab24a's committed intent at `apd-setup-a-2mbx#0` became unreadable and his retry bought a second domain ($15, D1 `vendor_spend_entries` vsp_3fedbbb8). NOTE the asymmetry that decided the fix's scope: only the CALLER-KEYED old form differs — the unkeyed form was byte-identical, so unkeyed rows never orphaned. No test could catch it, because every fixture seeds state through the CURRENT derivation. Fixed 2026-08-13 by a dated one-shot rebind (`engine/legacy-domain-intent-keys.ts`) + a literal-pinning guard (`test/persisted-key-derivations.test.ts`).
- **`domain_intents` has TWO writers with DIFFERENT derivations** — `domainIntentKey` (setup) and `replacementDomainIntentKey` (the deliverability loop's burn replacement). So "this key does not match the current setup derivation" NEVER by itself means "orphaned"; any sweep over that table that assumes one writer will rebind a live replacement key and re-create the orphan defect on the burn route.
- **A `domains` row with no committed intent is un-resumable AND un-adoptable.** `ownedDomainNames` (provisioning.ts:38) excludes it from candidates and `findAdoptableDomain` (:138-145) returns null for anything already recorded, while resume keys only off `domain_intents`. The two guards were built independently; their union strands the row permanently.
- **A freshly registered InboxKit domain cannot pass its own in-call DNS step.** `SET_DNS_BACKOFF_MS = [2_000]` gives ~2.3s of polling against a registration that takes ~32s to appear active in `/domains/list`, so every first-time purchase ends in a retryable `step: "domain DNS setup"` error by construction.
- **A test that reuses a COMPLETED idempotency key across a CHANGED request body asserts nothing.** `withRequestIdempotency` replays the stored response verbatim without running `fn`, so e.g. `domains:1` then `domains:2` under one key returns the first call's result and looks like a pass. A genuinely new request needs a new key; only a retry after a THROW re-runs (the claim is deleted on throw).
- **`vitest.config.ts`'s documented 5s-timeout flake is load-driven, not code-driven.** Under a loaded machine (other agents' batteries: load avg 25-70 observed 2026-08-13) heavy sequential-await files fail 6-8 tests at exactly ~5000ms in a FULL run and pass 14/14 in isolation. Before believing a regression, re-run the file alone. Also: a backgrounded `npm test` transforms sources LAZILY, so editing files mid-run silently invalidates that run as a baseline.

**Why:** all four are invisible to the test suite (tests inject their own clocks, stub fetch, and never build a real bundle end-to-end), so they only appear against a live paying tenant.
**How to apply:** on any ColdStart production incident, check the clock and the adapter-bundle kind before trusting timestamps or "no rows" evidence.
